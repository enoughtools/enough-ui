EnoughUI research · checked October 31, 2026 · recommendations, not implemented changes

Build the primitives, compose the agent patterns, expose a typed catalog.

Start with Trace and CodeBlock. Then ship reusable approval, composer, citation and agent-work patterns. Pilot json-render against EnoughUI’s own components, with TanStack AI as the first runtime integration example.

EnoughUI already includes Message, MessageScroller, Bubble, Marker, Attachment, Questionnaire and the general controls these patterns need. Its pinned October 2 shadcn baseline predates Trace and CodeBlock. The existing ToolRow is a branded convenience; its flat props do not provide Trace’s compound composition and state contract. Evidence: local parity contract, ToolRow source, and October upstream release.

What is worth studying

These projects address three different jobs: rendering agent activity, generating interfaces at runtime, and helping coding agents reuse a component library. Popularity below is a rounded GitHub-star snapshot from the repository API, not a measure of production adoption. Recommendations rely on maintained source and official documentation; this is not an exhaustive survey of launch videos on X.

Ranked additions

The priority reflects reuse, fit with the existing catalog and confidence in the upstream interface. These are proposed delivery batches, not effort estimates or verified implementations.

First · core

1. Trace

Adopt the complete upstream compound API, including line, icon, title, description and collapsible parts. Use it for tool activity, plans, queues, reasoning summaries and nested subagent work.

Preserve upstream status semantics: completed work has no status; running, pending and error are explicit. Keep cancellation and approval state in the adapter rather than inventing extra core statuses.

Interface and examples
First · core

2. CodeBlock

Adopt header/actions/content/line/footer parts, copy behavior, diff lines, wrapping and optional highlighting. Reuse it for terminal output and code changes.

Keep highlighting optional. EnoughUI’s proportional font rule remains in force; preserve exact copied text and test long lines, whitespace, selection and RTL surroundings.

Interface and behavior
Next · composition

3. Confirmation + answer receipt

Compose Item and Button for pending approvals; show the recorded outcome afterwards. Reuse Questionnaire for multi-question elicitation. Keep decision scope, persistence and execution host-owned.

Exercise pending, submitting, accepted, denied, expired and failed submission. A failed response should stay retryable, and a replayed transcript should not show live decision buttons.

shadcn pattern · Runtime edge cases
Next · composition

4. Prompt composer

Compose InputGroup, Textarea, Attachment and menus. Offer send/stop actions, upload feedback and model/effort controls as slots.

Preserve draft text on failures. Test IME composition, Enter versus Shift+Enter, file removal, disabled states and narrow layouts. Keep model lists and upload services supplied by the app.

Next · compositions

5. Sources + inline citations

Use Trace for grouped source activity and HoverCard/Popover with real links for inline references. Keep keyboard and touch access to the same source details.

Build Tool, Plan, Queue, Subagent, Terminal and TestResults as related Trace stories before deciding which wrappers deserve package exports.

Pattern catalog
Pilot · extension

6. Generated surface + catalog adapter

Start with Card, text, layout, choices, Table and forms mapped to EnoughUI. Expose schemas and named actions; register implementations in json-render. Add an optional surface wrapper for loading, invalid output, retry and empty state only if the pilot proves it is reusable.

Preserve stable IDs, input state and focus as chunks arrive. Reject unknown components/props and bind named actions to app callbacks. This is an EnoughUI extension, not a shadcn compatibility claim.

Catalog · Registry · Streaming
Other candidates and what to defer

Response / Markdown: useful once Trace and CodeBlock exist. Wrap a streaming renderer with our typography and citation/code slots; test partial fences and links, completion, abort and replay. Streamdown keeps plugins optional.

Artifact review: compose Card, Tabs, CodeBlock, Table and Sheet with app-owned apply/download callbacks. Add checkpoints and message branching when there is a real consumer. A preview iframe is a different integration from a catalog-rendered surface.

Defer: voice orbs, avatars with elaborate animation, model-logo packs, a second generic chat framework, a custom schema language and a collection of domain-specific weather/checkout/travel widgets. They add little to the immediate compatibility goal. Charts, tables, forms and existing Questionnaire should be reused before creating AI-prefixed alternatives.

How the first integrations should work

Keep the UI package independent of AI SDK, TanStack AI and CopilotKit. Adapter examples translate each runtime’s actual part types and callbacks into the same compositions. Do not silently merge tool-argument streaming, execution, approval and generated-result readiness into a single loading flag.

TanStack first: use stable 1.0 packages together and resolve tool-approval interrupts through the current API. Older examples using addToolApprovalResponse need migration. Shadcn’s TanStack helper is useful for deterministic story playback, but documents an incomplete subset of message parts; it is not evidence of full runtime parity. Check any helper against 1.0 before adopting its examples. 1.0 migration notes.

Generated UI second: use a server-readable catalog and a React renderer island in Astro. Native Astro can present completed static content; it cannot host live React state or callbacks without an island. Keep future A2UI/OpenUI mappings in separate adapters. Google’s October 29 integration guide reinforces using an application-owned catalog across agent frameworks.

What shadcn’s rules and PRs actually support

The repository’s contribution guide calls for coordinated style changes, documentation, registry rebuilding and feature tests. New-component requests begin as discussions. The relevant AGENTS.md is a generated Next.js guidance block, not a component admission policy; there is no root AGENTS.md at this snapshot.

The more useful interface guidance lives in the repository’s composition rules and styling rules: use existing compound parts, accessible overlay titles, built-in variants, semantic tokens and shared animation utilities. Compose loading buttons from Spinner and disabled state. These are published usage conventions; they do not constitute a promise to accept every PR that follows them.

Our policy inference: prefer small, composable interfaces and use the existing primitive for interaction semantics. Keep EnoughUI’s branding and renderer requirements explicit. Separate a generally reusable primitive from a workflow recipe or domain widget.

The implications are recommendations from this audit. They are not confirmed EnoughUI defects or a universal shadcn acceptance rubric.

Pin the interface snapshot; keep EnoughUI’s version independent

Do not synchronize our package number to the shadcn CLI number. The CLI, registry engine, React headless primitives and helpers have independent releases. A fixed CLI can still fetch changing remote registry content. Release policy · Fetch implementation.

The pin already exists

EnoughUI 0.5.0 targets the Radix catalog snapshot of October 2, 2026: 295a1f114a138f23b5dfee0e0c6812394dfeb90c. Keep that baseline until the next one is implemented and verified.

The subagent independently matched all 62 recorded source blobs against both this snapshot and observed upstream head c0d63c339d6cd2fc26135590a54cf1f362269451. The live Radix directory adds Trace and CodeBlock. This checks those source blobs; it does not establish unchanged documentation, metadata, dependencies or runtime behavior.

Pinned catalog · Observed live catalog

Qualify compatibility by provider + full commit + scope. Base UI is now the default for new shadcn projects, while Radix remains supported. asChild versus render, selection values and Accordion props differ. Retain the chosen Radix contract; evaluate a Base migration separately. API differences · Default change.

Recommended process to detect and adopt interface changes
  1. Freeze evidence: extend the existing parity manifest with pinned docs, registry metadata, hooks/utilities and exact reference dependency declarations. Verify file blobs and captured digests against the full SHA. Cache that evidence so ordinary CI is reproducible offline.
  2. Check actual interfaces: compile upstream usage fixtures against the reference and our source/packed public exports. Cover variants, sizes, refs, callback payloads, generic values and compound composition. Add negative fixtures so overly broad types cannot produce a false pass.
  3. Check behavior: map each documented capability and default to renderer or interaction evidence. The current gate checks export names and artifacts; it does not enforce prop compatibility. Six families record requiredProps that the checker never reads.
  4. Control dependency drift: exact pins for type-defining production primitives are the clearest initial policy; upgrade them promptly through the same tests. If we retain ranges, document and test supported resolutions. Our development lockfile does not freeze consumers’ resolutions.
  5. Discover upstream separately: use the existing weekly maintenance task to compare new modules, signatures, defaults, docs and dependencies. Record a compatibility gap when upstream changes; only advance the supported SHA after fixes, rebuilt artifacts and consumer checks pass.

Publish the baseline ID and exceptions in both renderer packages and release notes. Keep EnoughUI semver tied to our own public changes. After 1.0, incompatible prop/default/behavior changes require a major; during 0.x, explicitly use a minor for breaking changes and include migration notes. Do not append the baseline as semver build metadata: the existing release policy rejects that form.

Acceptance gate for new agent UI

  1. Interface: preserve the pinned Radix family’s exports, variants, props, refs, controlled state and documented composition. Label our conveniences and generated-UI schemas as extensions.
  2. Design: reuse existing parts and tokens; keep proportional typography everywhere, including logs and keyboard hints. Keep the compatibility font token mapped to the sans-serif token.
  3. Streaming: test partial input, partial output, terminal failure, cancellation, retry, reconnect/replay and simultaneous tool calls. Stable IDs must preserve user interaction.
  4. Accessibility: use semantic triggers and labels; verify focus restoration, keyboard/touch use, readable status text, reduced motion, long content and narrow viewports. Avoid announcing every token in a live region.
  5. Delivery: share variants/styles, supply native Astro presentation, keep stateful behavior in React islands, and add both Storybook renderers. Reuse stories for interaction and accessibility checks; do not build a separate showcase.
  6. Release: rebuild dist and renderer packages, verify public artifacts and consumer examples, then advance the compatibility baseline. Do not change the pin simply because upstream has moved.
Scope, confidence and reproducibility

This is a source/documentation audit, not a hands-on performance, accessibility or interoperability certification of the external libraries. Stars and latest activity were checked through GitHub’s repository API on October 31; Prompt Kit’s approximate figure comes from its repository page. Counts will change. No production-adoption ranking or exhaustive X-video survey is claimed.

Local inspection covered package exports/dependencies, the parity manifest and gate, maintenance/parity documentation, and current chat/ToolRow sources. Recommendations do not change runtime dependencies, package versions or the declared compatibility baseline.
